# Evaluation

The goal is a number that can be defended, not a demo that only looks good on one invoice.

## Synthetic data disclosure

Every document in `backend/eval/data/` is **made up** — generated by
[`backend/eval/build_samples.py`](../backend/eval/build_samples.py), not a real invoice from a
real business. That script and its ground-truth labels are committed, so the exact set is
reproducible. This first pass proves the pipeline and the checks work; it does not yet prove
performance on real, messy, real-world documents. See **Limitations** below before quoting
these numbers as more than that.

## Data set (v1 — 12 synthetic cases)

Twelve cases, each covering a specific thing worth testing rather than 12 near-duplicates:

| Case | What it tests |
|---|---|
| `clean_standard` | Baseline formal invoice, nothing unusual |
| `math_error_total` | Printed total is deliberately wrong — tests the **checks**, not extraction |
| `no_tax` | No tax line printed at all; subtotal should equal total |
| `many_items` | 9 line items — does it read the whole table? |
| `receipt_narrow` | Thermal-receipt layout instead of a formal invoice |
| `currency_usd` | USD with a `$` symbol instead of PKR |
| `missing_invoice_number` | No invoice number printed anywhere — should extract as null, not invented |
| `blurry_scan` | Same content as a clean invoice, rendered with blur + noise |
| `rotated_photo` | ~4.5° rotated, JPEG-compressed — simulates a phone photo, not a flat scan |
| `non_invoice_photo` | **Negative control**: not an invoice at all (meeting notes) |
| `single_item` | Minimal case: one line item, no tax |
| `explicit_zero_tax` | Tax is printed as `0.00`, not omitted — null vs. explicit-zero |

Each has a hand-authored label in `backend/eval/labels/<name>.json` with the exact fields the
app should extract, matching the schema in `app/services/validation.py`.

## Metrics

- **Field accuracy**: per-field match (numbers within 2 cents, dates exact, vendor/currency
  compared case-insensitively). Computed only over the 11 real-invoice cases —
  `non_invoice_photo` is scored separately since "correct" means something different for it.
- **Document accuracy**: every field on a document correct, including every line item.
- **Check effectiveness**: of the cases with a deliberately injected problem
  (`math_error_total`, `missing_invoice_number`), did `validate()` flag it? And on the clean
  cases, did it *avoid* flagging anything (false positives)?
- **Non-invoice handling**: what happens when a non-invoice file is uploaded (see the open
  question in the Results below).

## Procedure

1. `cd backend && ../.venv/Scripts/python eval/build_samples.py` — builds the 12 files (only
   needed once, or after editing the generator).
2. `../.venv/Scripts/python eval/run_eval.py` — runs each one through the **real** extractor
   configured in `.env` and compares to the label. This calls a real, metered API; it is a
   manual script, not part of the test suite or CI.
3. Full detail is written to `backend/eval/results.json`; the summary below is copied from its
   printed output.

## Results — run on 2026-09-27

**Model:** `gemini-flash-lite-latest` (see **A model change worth knowing about**, below, for
why this isn't `gemini-2.5-flash`).

| Field | Accuracy |
|---|---|
| vendor | 11/11 (100%) |
| invoice number | 11/11 (100%) |
| invoice date | 11/11 (100%) |
| currency | 11/11 (100%) |
| subtotal | 11/11 (100%) |
| tax | 11/11 (100%) |
| total | 11/11 (100%) |
| line items | 31/31 (100%) |

| Metric | Value |
|---|---|
| Documents fully correct | 11/11 |
| Injected problems caught by validation | 2/2 (`math_error_total`, `missing_invoice_number`) |
| False positives on clean documents | 0/9 |
| Non-invoice control (`non_invoice_photo`) | Correctly returned all-null fields, which our checks then flagged as missing — see the open question below |

**For comparison**, the same 12 cases were also run against `gemini-2.5-flash` (a heavier,
more capable model) before switching: 6/7 documents fully correct before its free-tier daily
quota was exhausted mid-run (see below) — one date was missed on `blurry_scan` that the lighter
model got right. On this small set, the lighter model was not worse.

## A model change worth knowing about

The app originally defaulted to `gemini-2.5-flash`. Mid-evaluation, it started failing with
`429 RESOURCE_EXHAUSTED`, and the response body was explicit about why:

> Quota exceeded for metric: `generate_content_free_tier_requests`, limit: **20**, model:
> `gemini-2.5-flash`

That's a **free-tier cap of 20 requests per day, per project, per model** — confirmed by
Google's own error response, not a guess. Independent reporting corroborates this: Gemini
2.5 Flash's free daily limit was cut from roughly 250/day to about 20/day around December
2025.¹ Twenty requests a day is unworkable for even light real use or a reviewer trying the
app more than a couple of times.

Switching to `gemini-flash-lite-latest` fixed this: the full 12-case set ran without hitting
any limit, and accuracy on this set was equal or better. That's now the default
(`GEMINI_MODEL` in `.env`). The trade-off: it's a "latest" alias, so Google can change which
model version it points to over time — a pinned version would be more reproducible but risks
the same kind of sudden deprecation `gemini-1.5-flash` and `gemini-2.5-flash-lite` already hit
during this project. Re-run `eval/run_eval.py` after any Gemini-side change to confirm accuracy
hasn't regressed.

¹ [Gemini API Free Tier Rate Limits guide](https://www.aifreeapi.com/en/posts/gemini-api-free-tier-rate-limits) — third-party reporting, not an official Google source; Google's own dashboard at [ai.dev/rate-limit](https://ai.dev/rate-limit) is the authoritative place to check current limits.

## Open question: non-invoice uploads

`non_invoice_photo` extracted as all-null fields, which then got flagged by the completeness
checks as "missing vendor / missing total / etc." — so nothing crashed and nothing was
silently approved. But the review screen for that case would just show a form full of blanks,
which is a confusing experience rather than a clear "this doesn't look like an invoice"
message. Worth a dedicated fix (see the enhancements list) rather than something this eval
set can score cleanly one way or the other.

## Limitations (read before citing these numbers)

- **12 samples, all synthetic.** This is enough to prove the pipeline and the checks work as
  designed, and to catch the kind of model/quota surprises documented above. It is *not* enough
  to claim a general accuracy rate — 100% on 11 documents I generated myself is a much weaker
  claim than 100% (or 85%, or whatever it turns out to be) on real invoices from real vendors.
- **No handwriting, stamps, torn/creased paper, or multiple languages** — real invoices have
  all of these and synthetic ones don't capture that well.
- **Every synthetic document renders in a legible, consistent font.** Real phone photos and
  scans vary far more than the blur/rotation simulated here.
- **Next step:** add a v2 batch of real invoices/receipts (redacted) if any become available,
  re-run, and report the two data sets separately rather than merging them — mixing synthetic
  and real results into one number would overstate confidence.
